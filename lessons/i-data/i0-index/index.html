I0 · I 卷導讀：資料放哪裡，比怎麼寫 SQL 更重要

記憶體、Redis、資料庫各管什麼；為什麼 tick 熱路徑絕對不該狂寫庫。

data

這章你會搞懂什麼

H 卷把「一局怎麼跑」講清楚了：Session、Room、Tick、權威狀態。
I 卷要回答另一個同樣致命的問題：這些狀態，哪些只活在記憶體、哪些進快取、哪些一定要進資料庫？

遊戲 Server 跟一般 CRUD 網站不一樣。網頁後台可以「每個請求讀寫一次 DB」；對局迴圈若每 tick（例如 20Hz）都打 Postgres，你很快會發現：

  • 延遲抖到玩家覺得「頓」
  • 連線池被打爆
  • 磁碟 I/O 成為瓶頸
  • 一重啟，半途寫入還可能留下半殘資料

所以這卷的核心心智不是「學會 ORM」，而是 分層：熱的放記憶體、跨進程可丟一點的放 Redis、必須活過重啟／關服的才進 DB，而且寫入時機要卡在事件邊界，不是卡在 tick。

讀完 I 卷，你要能指著 Arena Mini（或你自己的房間）說：座標為什麼不落庫、對局結果什麼時候寫、排行榜為什麼適合 Redis、錢包為什麼不能只信快取。

先建立分層地圖

層 例子 延遲／一致性 進程掛了會怎樣
記憶體（Room） 座標、血量、tick、準備狀態 最快；權威就在這 沒了（除非你先 flush）
快取（Redis 等） 在線、排行榜、pubsub、短 TTL session 快，可跨進程 視持久化設定；別當唯一真相
資料庫 帳號、庫存、購買、賽季結算 慢但持久 還在（交易做對的前提下）

一句口訣：不是什麼都寫 DB。Tick 熱路徑只碰記憶體。

生活比喻：對局像球賽進行中的記分板——你不會每秒把黑板數字刻進石碑；終場、換邊、發獎才正式入冊。Redis 比較像「場邊大螢幕／廣播」，方便很多看台一起看，但不保證離線的人補得到每一句廣播。

本卷地圖

章 主題 你會練到什麼
I1 持久化邊界 熱／冷路徑；什麼事件才該寫
I2 database/sql 模式 連線池、context、Repo 介面

遊戲 Server 會用在哪

對 Arena Mini 這種教學局：

  • 進行中座標／輸入緩衝：Room 記憶體，跟 tick 走
  • 對局結束結果：事件邊界寫出（log、之後可接 DB／佇列）
  • 帳號資產（若你之後加商店）：DB 交易，絕不是每幀更新

正式專案常再加 Redis：多 Gateway 要查「這人在哪個房間」、跨服排行榜、短 TTL 斷線重連票。單機 demo 可以不裝 Redis；心智模型要先有，擴展時才不會把所有東西塞進一個 Postgres 表格硬撐。

動手練習

讀完整卷前，先用這題自我測驗（讀完 I1～I5 再對答案也行）：

  1. Arena Mini（或你腦中的 1v1 房間）列出至少 5 種狀態。
  2. 各標成「記憶體／Redis／DB」。
  3. 特別寫一句：為什麼玩家座標不該每 tick 寫資料庫。

答得出「因為延遲、負載、權威在 Room、崩潰語意可接受／不可接受要分開想」——這卷就對了。

常見坑

  • 一看到「要存檔」就每幀寫庫：熱路徑會先死。
  • 把 Redis 當永久金庫：重啟、淘汰、叢集故障時，錢與庫存會哭。
  • 沒分「可丟的進行中局」跟「不可丟的資產」：結算語意全混在一起，之後很難補。
  • Room 物件直接握著 *sql.DB 在 tick 裡 Query：邊界錯了；I1、I2 會反复打這點。
