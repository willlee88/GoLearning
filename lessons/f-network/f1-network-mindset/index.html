F1 · 網路心智模型

延遲、吞吐、丟包與遊戲手感；可靠傳輸不等於即時。

networkgame-server

這章你會搞懂什麼

網路不是「函式呼叫比較慢一點」而已。中間有距離、有路由器、有可能丟包、有人手機切基站。

你要建立的心智：

  • 延遲（latency）：一去一回要多久（常講 RTT）
  • 抖動（jitter）：這次 30ms、下次 80ms，不穩
  • 吞吐（throughput）：單位時間能搬多少資料
  • 丟包／重傳：TCP 會重傳，但你的「即時手感」可能已經過期
  • 可靠 ≠ 即時：TCP 保證送到且有序，卻可能卡在隊頭

本站實作主軸是 TCP／WebSocket + 權威伺服器狀態；UDP 只做概念對照，不要求你先寫一套 UDP 協定。

先跟 Python 對一下

物理層與協定兩邊一樣。你在 Python 用 asyncio 或 threads 時也要設 timeout；Go 這邊用 context、SetDeadline 把超時講清楚。

差別比較常出在：預設 API 很方便就阻塞讀，新手忘了設 deadline，連線假死時 goroutine／thread 掛一輩子。

怎麼寫（先記數字直覺）

情境 量級（示意）
同機 loopback < 1ms
同城 RTT 數 ms～數十 ms
跨洲 RTT 100ms+

遊戲 tick 若是 20–60Hz（每幀 16–50ms），RTT 會直接吃掉「手感預算」。同機覺得超順，不代表玩家遠端也順。

記住三句口訣：

  1. 小狀態同步常常是延遲與訊息率問題，不是頻寬跑滿。
  2. 沒有 deadline 的 Read，是生產事故候補。
  3. 廣播很容易變成流量放大器。

為什麼這樣設計／底層在幹嘛

延遲 vs 頻寬

傳 200 byte 的狀態，瓶頸多半是「多久能往返／多久能排程送出」，不是「光纖不夠粗」。優化方向：少聊廢話、合併訊息、別每幀全員全量乱打。

TCP 隊頭阻塞（Head-of-Line blocking）

TCP 保證有序。前面一個包丟了在等重傳，後面已經到的資料也會卡著不交給你的應用。對「最新位置最重要、舊位置可丟」的玩法，這是痛點——所以有人用 UDP。但 UDP 要把可靠、順序、擁塞自己補齊，成本很高。教學與很多遊戲類型（回合、休閒即時、權威房間）用 TCP／WS 完全合理。

廣播放大

50 人同房、每人每 tick 都把全場狀態廣播一遍，粗算會往 O(N²) 訊息量長。實務要：興趣管理、只送 delta、降頻、分線程／分房。

背壓（backpressure）

客戶端讀得慢 → Server 寫入緩衝堆起來 → 記憶體漲或阻塞寫 goroutine。要有有界佇列、可丟棄的訊息策略、慢客戶踢除——後面 lab 會碰到「寫鎖／廣播」。

進階可先略過

  • Nagle、delayed ACK：小包頻繁時的延遲怪癖。
  • 行動網路 NAT：中間盒可能默默丟閒置連線 → 所以要心跳（F7）。

遊戲 Server 會用在哪

權威 Server（規則在伺服器算）常被選，不是因為「TCP 最快」，而是狀態可預期、較好反作弊、瀏覽器能用 WS。預測與延遲補償是 H 卷以後的進階題；先把連線與協定做對。

請丟掉的舊習慣

  1. 預設阻塞讀、不設 timeout。
  2. 「TCP 不會丟」所以應用層不必重連、不必冪等——中間盒會斷，重送會變成開兩槍。
  3. 只在本機測就宣稱同步方案沒問題。

動手練習

必做

  1. 用文字粗算：30Hz、50 人同房、每 tick 對每人廣播 200B 全量，Server 每秒送出大約多少資料？（提示：先算每 tick 總 bytes，再 ×30。）
  2. 列出你會為連線設的三種 timeout：握手／讀閒置／寫。

選做

  1. 查你家寬頻標稱的「延遲」數字，跟同城／跨洲量級對照。

常見坑

  • 把頻寬升級當延遲解藥：玩法手感常常不吃這套。
  • 全量狀態每 tick 狂廣：先算流量再寫碼。
  • 忽略抖動：平均 RTT 低但偶發 200ms，玩家照樣罵。

延伸閱讀

  • TCP 概念：RFC 793（可略讀，建立「可靠位元組流」印象即可）
