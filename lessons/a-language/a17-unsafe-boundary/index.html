A17 · unsafe：知道它存在，平常別碰

unsafe 能打破型別與記憶體安全假設。教學目標是認得出、拒絕在業務裡無測量亂用。

unsafe

這章你會搞懂什麼

unsafe 套件能打破 Go 平常給你的型別與記憶體安全假設，用在極致優化或跟 C 互通這類場景。

這章的學習目標很明確：認得出、說得出風險，並且拒絕在房間規則／業務路徑無必要地使用它。遊戲 Server 要加速，先 profile，不要先黑魔法。

Python 對照

有點像 ctypes 或直接玩弄記憶體配置——多數 web／遊戲後端業務根本不需要。你在 Python 很少為了省一次拷貝去改物件頭；在 Go 也一樣，先把架構做對。

怎麼寫

這章故意不給「來一段超酷 unsafe」當日常範例。你要記住的是使用門檻：

  • 在 unsafe 之外，標準庫與編譯器給你的保證比較強
  • 一用 unsafe，可攜性、版本升級、race 推理都變難
  • Code review 應視為紅旗：要有測量、要有註解、要有替代方案被否決的理由

若你在依賴裡看到它，先問「這是編碼套件熱路徑還是有人炫技」。

細節

它大概能幹嘛（概念級）

  • unsafe.Pointer 在不同指標型別間轉換
  • 偷看對齊、大小，做極端布局假設
  • 某些 string／[]byte 零拷貝轉換（經典也危險）

這些東西的共同點是：編譯器比較難幫你擋壽命與別名錯誤。指標還指向已失效資料時，後果是未定義行為等級的痛苦，不是友善 panic。

優化順序請排後面

正確 → 可測 → 減少分配／減少廣播 → 演算法 →（真的需要）再考慮 unsafe。

進階可先略過

  • 與 cgo 的交界、指針通過 Go／C 邊界的規則。
  • 各版本 runtime 對字串內部表示的假設（這也是為什麼零拷貝轉換危險）。

遊戲 Server 會用在哪

狀態同步若太貴，優化順序通常是：

  1. 少廣播（誰需要誰才收）
  2. delta／降頻
  3. 更緊的二進位格式
  4. 最後才考慮 unsafe 或極度定制的序列化

Room 規則檔出現 unsafe，預設當作設計氣味。

請丟掉的舊習慣

  1. 「感覺會比較快」就上黑魔法，連 pprof 都沒跑。
  2. 從網路上的 snippet 複製 string／[]byte 零拷貝轉換，卻不懂生命週期。
  3. 用 unsafe「繞過」匯出規則或型別系統——那是在跟未來的自己打仗。

動手練習

必做

  1. （可選）搜尋你依賴裡誰 import 了 unsafe。
  2. 寫下三條「禁止在 Room 規則使用 unsafe」的理由。

選做

  1. 讀 unsafe package 文件標題與警告段落，整理成自己的檢查清單。

常見坑

  • 為了少一次拷貝引入未定義行為。
  • 升級 Go 版本後內部布局假設失效。
  • review 沒人看得懂 → 變成沒人敢動的詛咒碼。
