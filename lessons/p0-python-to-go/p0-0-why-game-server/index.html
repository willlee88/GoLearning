P0.0 · 為什麼要拿遊戲 Server 當練習目標？

這不是遊戲美術課。我們用一個迷你遊戲 Server，把後面學的 Go 技能接到能跑、能驗證的東西上。

範例：demo/arena-mini

metagame-servermindset

這章你會搞懂什麼

GoLearning 不是教你做遊戲美術、關卡或 Unity 的課。

「遊戲 Server」（game server）在這裡是整條學習路徑的應用錨點：型別、錯誤處理、一次做很多事（concurrency）、網路、協定、誰說了算的狀態（authoritative state）、觀測、優雅關機……都會接到一個你能雙開瀏覽器驗證的小東西上。

那個小東西叫 Arena Mini。它是終點實驗室，不是作品集展示。

讀完這章你要能用自己的話講清楚：為什麼本站不拿 Todo API 當主線，而要弄一個「有房間、有節奏、有多人」的後端。

為什麼需要一個「終點」？

只讀文章很容易變成：章很多，但學完不知道用在哪。

有一個終點 demo，你就能反問自己：

我學的這些，合在一起能不能撐住一個即時、多人、有狀態的後端？

只讀文章時你可能覺得 有 Arena Mini 之後
「channel 好像懂了」 連線迴圈 + 房間 tick 真的在跑
「記得要處理 error」 滿房／階段不對／壞輸入都有明確路徑
「race 很重要」 玩家清單與廣播有鎖、有測試
「HTTP 我會寫」 還有長連線 WebSocket 與狀態廣播

沒有終點，知識容易散掉；有終點，每一章的「遊戲 Server 會用在哪」才有落點。

為什麼選「遊戲」而不是 Todo API？

CRUD（新增／查詢／改／刪）也能教 HTTP，但比較難一次逼出這些能力：

  1. 長連線 — 不是 request 結束就沒事，連線可能掛很久
  2. 多人共享、會被改的狀態 — 誰擁有資料、同時改會不會打起來（race）
  3. 時間節奏（tick） — 固定步進更新世界，不是每個請求各過各的
  4. 權威與信任邊界 — 客戶端只送「我想做什麼」，真相在 Server
  5. 廣播放大 — 人數一多，訊息量與 CPU 怎麼爆

這些正好是 Go 常被用在即時後端、閘道、遊戲 Server 的原因，也貼近「你會一點 Python、想認真搞懂 Go」的目標。

刻意做得很小

有 沒有（刻意不做）
進房、Ready、移動、state 華麗畫面、關卡編輯器
權威 input、大約 20Hz tick 完整 MMO、無縫大地圖
metrics、優雅關閉 付費、帳號大系統

為什麼要小？

  1. 焦點在 Server 與 Go，不是 Unity／美術
  2. 短時間能跑通，不拖垮整門課
  3. 規則邏輯可以單獨測試，跟網路 I/O 分開

之後若加碰撞、得分、Ended，那是玩法完整度加分，不是這門課存在的理由。

先跟 Python 對一下

你可能用 Flask／FastAPI 寫過 API。那些多半是：

  • 短請求進來 → 查庫或算一下 → 回傳 → 結束
  • 通常沒有「很多客戶端同時盯著同一塊記憶體裡的世界」

遊戲 Server 更接近：

  • 一個長生命週期的行程一直開著
  • 多個客戶端不斷送事件進來
  • Server 記憶體裡有一份「權威世界」

Go 的價值在這種場景特別明顯——後面章會一層層拆給你看。

請丟掉的舊習慣

  1. 「這課要培養遊戲企劃」 — 否，錨點是後端工程。
  2. 「先做出完整遊戲再學 Go」 — 否，先最小能跑的閉環。
  3. 「聊天室就夠了吧」 — 能練連線，但較難練 tick、權威狀態、廣播節奏。

動手練習

必做

  1. 用自己的話寫三句：為什麼本站用遊戲 Server 當錨點（不要抄標題）。
  2. 打開學習路徑，找出 H 卷與 demo/arena-mini 大概在哪。

選做

  1. 假設改成「協同白板」當終點：列出哪些能力還蓋得到、哪些會變弱（例如 tick、權威、廣播）。

常見坑

  • 把 Arena Mini 當成要交的作品集遊戲 → 你會分心去做美術，反而跳過 Server 本質。
  • 覺得「太小沒誠意」→ 小是刻意的；先能驗證閉環，再加玩法。
  • 想跳過 P0 直接抄 Server 範例 → 後面的錯誤、型別、併發會一直撞牆。
