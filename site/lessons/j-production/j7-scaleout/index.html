J7 · 水平擴展提醒：有狀態房間不能亂 round-robin

搞懂 sticky／房間親和、Gateway 與 Game 切分；為什麼同一房的封包不能隨便打到不同機器。

scale

這章你會搞懂什麼

單機優化（J6）之後，下一步常有人說：「沒關係，我們水平擴展（scale out）多開幾台。」

對 無狀態 HTTP（誰來處理都差不多）這很常見。
對 有狀態的即時對局——房間狀態活在某台機器的記憶體裡——亂加機器會變這樣：

  • 玩家 A 的 input 打到機器 1
  • 玩家 B 的連線在機器 2
  • 兩台各有一份「真相」→ 不同步、互撞、幽靈局

這章目標不是讓你立刻上 K8s 叢集，而是建立擴展邊界：

先知道什麼不能做；真要做時，房間要有「亲和／路由」策略。

Python 對照

Python／Web 遊戲即時對局
Django／Flask 多 worker + sticky session 同源問題：會話／狀態在哪裡
無狀態 JWT API 好擴 房間 tick 狀態通常「有狀態」
Celery 多 worker 搶任務 對局不能隨便搶同一房的寫入

你若做過「負載平衡打到不同 worker 導致 session 丟失」，感覺是一樣的，只是遊戲更敏感：每秒几十次狀態更新。

怎麼寫（先記策略，不是先抄程式）

常見策略：

1. Sticky／房間親和（最常用的思考起點）

同一 room id 的流量，進同一 Game 進程。

做法直覺：

  • Gateway（閘道）無狀態，負責連線、驗證、轉送
  • Game 有狀態，擁有房間記憶體
  • 用 room id 做一致性雜湊（consistent hashing）或查「房間目錄服務」：這個房在哪台

教學結論：

先垂直優化單機 Room；真要擴展，按 room id 黏住，而不是對 WS 亂 round-robin。

2. 遷移房間（少用、複雜）

把整房狀態從機器 A 搬到 B。
要處理：暫停、序列化、搬運、恢復、對連線重掛。成本高，通常是「這台要下線」才做。

3. 把狀態外置到 Redis 等

每 tick 或每次操作都跟外部存儲同步。
代價：延遲、複雜度、一致性頭痛。適合某些 presence／大廳資料；高頻權威對局很少「每件事都遠端寫」。

為什麼這樣設計／底層在幹嘛

為什麼 round-robin WebSocket 會炸？

Round-robin（輪詢）假設每個請求可獨立處理。
但 Room 是：

  • 單一（或少數）權威寫入者
  • 連續的 tick 與 input 隊列
  • 廣播成員名單在記憶體

封包被拆到兩台 = 兩個權威，規則崩壞。

Gateway 無狀態 + Game 有狀態

這是常見切分：

Client → Gateway（連線、認證、路由）→ Game（房間、tick、權威）
                 ↘ Match／目錄服務（這房在哪）

好處：

  • Gateway 可多開，擋斷線重連、TLS
  • Game 按房間水平加機器
  • 匹配服務（matchmaking）與對局服務分離：大廳排隊不必跟 20Hz tick 搶同一進程

最終一致與全局廣播

跨機器的「全伺服器公告」「跨房聊天」常靠 pub／sub。
你要接受：不是同一瞬間所有人看到同一句話——這叫最終一致。
對局內權威狀態則通常不能靠「大家晚點一致」湊合。

觀測也要跟著變

多實例時：

  • 每實例自己的 /metrics
  • 上面要有彙總（Prometheus 多 target）
  • 日誌帶 instance／room，不然你不知道該看哪台

進階可先略過

  • 一致性雜湊虛節點、房間目錄的 CAP 取捨
  • 多活與異地備援
  • 無縫遷移協議細節

Arena Mini 維持單進程是故意的：先把單機正確性與觀測做滿。

遊戲 Server 會用在哪

讀完這章，你應能在紙上畫：

  • 兩個 Gateway
  • 兩個 Game
  • 玩家帶著 room=abc 進來時，如何保證進同一 Game

以及標註：哪些元件可以隨便水平擴，哪些不行。

Arena Mini 文件與課程標明擴展邊界——不是功能沒做完就算失敗，而是讓你知道下一步要買什麼票。

請丟掉的舊習慣

  1. 無狀態 HTTP 思維硬套即時對局。
  2. 多副本搶寫同一份記憶體地圖（沒有共享記憶體魔法）。
  3. 「先多開 pod，掛了再查為什麼不同步」。
  4. 還沒量單機就上微服務，複雜度爆炸。

動手練習

必做

  1. 畫「兩 Gateway + 兩 Game」的房間路由草圖：標出 room id 在哪裡決定去哪台。
  2. 用三句話回答：為什麼同一房的 WS 不能在兩台 Game 之間 round-robin？

選做

  1. 寫下：大廳 presence 用 Redis、對局狀態留在 Game 記憶體——這樣切的優缺點各一。
  2. 設想 Game 要下線時，沒有遷移方案，你會如何「拒新進房 + 打完現有房 + 引流」？

常見坑

  • 只黏 IP／連線，不黏房間：重連換線路後進錯機器。
  • 目錄服務與真實房間不一致：房已關但目錄還指著；要有心跳與對帳。
  • 全局鎖在外部存儲：表面上擴了，實際上所有房搶一把 Redis 鎖。
  • 每實例 metrics 看起來都健康，彙總才發現總流量爆：記得看整體。
