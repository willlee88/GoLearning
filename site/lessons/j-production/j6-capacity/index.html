J6 · 容量與廣播放大：人一多，流量不是線性的

用粗估公式感受頻寬與 CPU；搞懂全量互相廣播為何接近 O(N²)，以及可以怎麼降流量。

capacity

這章你會搞懂什麼

壓測會告訴你「炸了」；容量思考告訴你「大概為什麼會炸、多快會炸」。

遊戲房裡最常見的隱藏殺手是 廣播放大：

  • 1 個人動一下，若你要讓房裡 N 個人都看到完整快照
  • 每 tick 都做一次
  • 人數上升時，出站流量與編碼 CPU 會衝很快

讀完你要能：

  1. 用一條粗估公式算「每房出站大概多少」
  2. 解釋為什麼「全量互相廣播」在人數上升時很痛
  3. 說出至少一個降流量手段（delta、降頻、興趣管理……）

Python 對照

觀點 說明
公式與語言無關 Python／Go 都會被架構打臉
慢往往不在「語言」 JSON 編碼、鎖、廣播次數、記憶體拷貝才是常客
「先上線再看」 兩邊都常見；人一多就後悔

口訣：語言很少是第一瓶頸，狀態同步策略常常是。

怎麼寫（先算，再優化）

粗估出站：

出站 ≈ 房間數 × 每房人數 × 每 tick 快照大小 × tick Hz

若「每個收件人都收到一份完整快照」，而快照裡又包含所有人狀態，人數為 N 時，常會看到近似：

每 tick 出站工作量 ≈ N（收件人）× 快照大小(隨 N 變大)

也就是隨 N 變差得比線性更兇——你常聽到的 O(N²) 殺傷力直覺。

小例子（示意）

假設：

  • 4 人房
  • 每份 state 約 200 bytes（先當壓縮／二進位後的理想值；JSON 通常更大）
  • 20Hz tick

每房出站大約：

4 × 200 × 20 = 16_000 bytes/s ≈ 16KB/s

看起來很小。換成 50 人同房、同樣 200B、20Hz：

50 × 200 × 20 = 200_000 bytes/s ≈ 200KB/s

若快照大小其實隨人數變長（每人多一段 JSON），例如平均變 2KB：

50 × 2000 × 20 ≈ 2MB/s

還只是「一個房」。再乘房間數、再加 TCP／WS 開銷、再加 CPU 編碼——你就知道為什麼要先算。

（數字是示意，重點是數量級與曲線，不是精確會計。）

為什麼這樣設計／底層在幹嘛

為什麼是「放大」而不是「線性」？

因為成本常同時被兩件事推高：

  1. 收件人變多：同一份世界，要寫出更多次 socket
  2. 負載變大：快照含更多玩家／物件，編碼與記憶體配置變貴

兩者疊加，體感就像 N²。H7 狀態同步若採「每次全量 state」，教學好懂，但人一多先痛。

CPU 常死在哪？

  • JSON 編解碼（方便但偏貴）
  • 每次廣播 make 新 buffer、字串拼接
  • 持鎖做網路送出：別人進房／input 都在等這把鎖——大忌；常見作法是先在鎖內拷貝要送的資料，鎖外再送
  • 過多 goroutine 或無界佇列（C8 背壓）把排程拖垮

GOMAXPROCS 與多核

Go 預設會用多核，但：

  • 單房單一 tick goroutine 仍可能把「邏輯」綁在一條熱路徑
  • 廣播可以用有限 worker，但別幻想「加核就能線性救 N² 協定」

先優化協議與資料量，再談機器規格。

降流量的常見方向

手段 人話
Delta／增量同步 只送改變的部分，不是整包 state
降頻 遠景、觀戰、非關鍵物件少送幾次
興趣管理（AOI） 只送你附近／你看得到的實體
二進位協定 同樣資訊更小（如 Protobuf，見 K 卷延伸）
房間人數上限 最簡單的產品向保险丝

沒有銀彈：你要在「手感」與「成本」之間取捨。

進階可先略過

  • 優先級頻道（移動 vs 聊天）
  • 客戶端預測與和解對頻寬的影響
  • 壓縮演算法選型

遊戲 Server 會用在哪

Arena Mini 教學採全量 state，方便你在 load-client 下用身體感受曲線。
觀察建議：

  1. 固定 Hz，把同房人數拉高，看 messages_out 與 CPU
  2. 對照你用公式估的數量級，是否「同方向」
  3. 想一件你願意做的降流量改動（即使只寫在紙上）

之後真要做大房間或大世界，J6 這條公式會一再出現。

請丟掉的舊習慣

  1. 「先上線再看」完全無容量圖。
  2. 複製 AAA 大世界架構，實際只有 10 人房。
  3. 以為換成 Go 就自動比 Python 撐十倍——協定不變，放大還在。
  4. 持鎖廣播到網路。

動手練習

必做

  1. 估算：50 人同房、20Hz、每份快照 200B 的出站（先用線性公式）；再假設快照變成 2KB，重算一次。
  2. 提出一個降流量手段，並寫一句「它犧牲了什麼手感／複雜度」。
  3. （建議）對 Arena Mini 跑一輪 load-client，把 messages_out 變化跟你的估算對照看。

選做

  1. 若 tick 從 20Hz 降到 10Hz，出站怎麼變？對操作手感可能有什麼影響？
  2. 讀 H7，用自己的話對照「全量 vs 增量」。

常見坑

  • 只算頻寬、不算 CPU：很小的封包也可能因為編碼與 syscall 次數把 CPU 吃滿。
  • 用尖峰當平均：活動瞬間進房、大範圍技能，曲線會刺。
  • 優化錯層：還沒量就先上微服務；其實單房協定改一下就夠。
  • 忽略多房總和：每房都「還好」，乘上 500 房就不還好。
