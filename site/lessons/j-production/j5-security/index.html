J5 · 安全基線：客戶端說的話，預設都不可信

驗證命令、限制大小與速率、守住秘密與信任邊界；權威 Server 是反作弊第一層，但不是全部。

security

這章你會搞懂什麼

遊戲客戶端在玩家手上，等於在「對方完全可控的環境」裡跑。
改封包、重放、刷指令、灌垃圾資料，都比你想的容易。

所以心智模型很硬的一句話：

客戶端不可信。能信的只有：你 Server 驗證過、計算過、授權過的結果。

這章不教你變成資安專家，只建一條基線（baseline）：沒有這些，後面什麼 matchmaking、廣播優化都像沙上蓋樓。

讀完你要能：

  1. 列出至少五項 Server 該做的檢查
  2. 說明為什麼「前端藏管理員按鈕」不算安全
  3. 解釋為什麼客戶端直傳座標（pos）很危險（呼應 H4 權威）

Python 對照

Python Go／遊戲後端
Pydantic／serializer 驗證 手寫驗證或驗證庫；範圍、長度、枚舉
rate limit middleware 每連線／每玩家令牌桶或固定視窗計數
Django permission 房間身份、phase、是否輪到你
不把 secret 打進 log 同樣；J1 已強調

層次很像 Web API；差別是：長連線 + 高頻 input，速率限制與訊息大小限制更常被打穿。

怎麼寫（基線清單）

把下面當成上線前的檢查表，不必一次完美實作，但每項都要有態度：

1. 驗證所有命令

  • 型別對不對？欄位缺不缺？
  • 數值在不在範圍？（例如 input 的 dx,dy ∈ [-1, 1]）
  • 當前 phase 允不允許？（lobby 不能亂套 playing 專用命令）
  • 這個人是不是這個房間的成員？

非法就拒絕，並可打 Warn（別把惡意流量打成 Error 洗版）。

2. 限制訊息大小與速率

  • 最大幀長／最大 JSON 大小：防止一個連線塞爆記憶體
  • 每連線每秒最多 N 個 input／聊天：防止刷指令拖垮 tick
  • 暱稱長度、字元集：防止超長字串、奇怪控制字元

3. 認證與會話（生產）

教學 demo 常用 name query 進房；真的上線要：

  • 登入後發 token（令牌），連線時驗證
  • session 過期、重連策略（H2／延伸任務）
  • 別只靠「我知道房間代號」當授權

4. 傳輸與部署

  • 公網用 TLS（HTTPS／WSS）
  • 管理 API 與玩家口分離（不同 port 或網段）
  • debug／pprof／管理員介面不要預設暴露在公網

5. 日誌與秘密

  • 不打密碼、token 全文（J1）
  • 設定檔與環境變數管理秘密，不進 git

最小程式直覺（速率限制示意）

// 概念示意：每連線獨立計數，超限就丟棄或關閉
if n := client.inputsThisSecond; n >= maxInputsPerSec {
    // reject or disconnect
    return
}
client.inputsThisSecond++

真實實作可用時間窗重置、令牌桶；先有「有上限」比沒有重要。

為什麼這樣設計／底層在幹嘛

權威 Server 是反作弊第一層，不是全部

H4 講過：位置、碰撞、得分應由 Server 算。
客戶端只送「我想往哪走」的 input，不送「我已經到某座標」的結論。

為什麼直傳 pos 危險？

  • 玩家可以改封包瞬移、穿牆、搶分數
  • 你變成「誰喊得兇誰贏」，規則崩盤
  • 重放攻擊更容易（直接重送有利座標）

權威之後仍要防：加速器（異常 input 頻率）、協議濫用、經濟系統刷物——那些可能還要統計、風控、回放。基線是先別把大門打開。

信任邊界（trust boundary）

畫一條線：線外是客戶端與公網，線內是你的進程與資料庫。
跨線的一切都要驗證。
「我們前端會檢查」只減少誠實用戶的誤操作，擋不住修改過的客戶端。

房號枚舉與資訊洩漏

若房間 id 是 1,2,3...，有人會掃一遍嘗試加入。
緩解：足夠隨機的 id、需要票據／邀請、權限檢查、速率限制。
/rooms 這類管理資訊也不要對全世界無條件公開（教學 demo 可鬆，生產要收）。

瀏覽器 WebSocket 的 Origin

瀏覽器環境可檢查 Origin，降低簡單的跨站濫用。
原生遊戲客戶端較不吃這套，仍要靠 token 與協定驗證——Origin 不是萬能盾。

進階可先略過

  • WAF、機器人分數、裝置指紋
  • 反外掛驅動級方案
  • 正式威脅建模（STRIDE 等）

新手先把「驗證、限速、秘密、權威計算」做穩。

遊戲 Server 會用在哪

Arena Mini 已拒絕非法 input（範圍等）；速率限制可當練習自己加。
想像這些攻擊面：

行為 沒有基線時
每秒上千 input tick／鎖／廣播被拖死
超大 JSON 記憶體尖峰、GC 爆炸
掃房號 進別人對局、騷擾
直傳座標 作弊橫行
管理 API 裸奔 直接關房、改分

壓測（J4）找的是「容量」；安全基線找的是「惡意或異常流量下你還活不活」。兩者都要。

請丟掉的舊習慣

  1. 前端隱藏「管理員按鈕」就當安全。
  2. 預設把 debug、pprof、寬鬆 CORS 開在公網。
  3. 「先上線，被打了再補驗證」。
  4. 相信客戶端算好的分數、金錢、背包。

動手練習

必做

  1. 寫下 3 個你會加在 Arena Mini（或同類 Server）的 rate limit（例：每連線每秒 input、每連線每秒聊天、每 IP 每分鐘建連）。
  2. 用自己的話說明：為什麼客戶端直傳 pos 危險？正確做法應送什麼？（呼應 H4）
  3. 檢查你日誌／設定有沒有可能印出秘密——有的話改掉。

選做

  1. 為暱稱加上最大長度與允許字元集，測超長字串。
  2. 畫一張「信任邊界」：標出客戶端、Gateway、Game、DB，哪些箭頭要驗證。

常見坑

  • 只驗證「開心路徑」：記得測缺欄位、NaN、超大數、錯誤 phase。
  • 限速做成全域一把鎖：可能變成新瓶頸；通常「每連線狀態」較合理。
  • 拒絕時回太多內部細節：給攻擊者提示；對玩家給簡潔錯誤即可。
  • 以為權威 = 絕對安全：權威防的是狀態說謊；灌流量、挖洞、社工仍要另外防。
