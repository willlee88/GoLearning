I1 · 持久化邊界：什麼時候才該寫進硬碟

熱路徑 vs 冷路徑；事件邊界寫入；帳號資產跟進行中對局為什麼不能同一套語意。

persistencegame-server

這章你會搞懂什麼

「持久化」（persistence）白話講就是：讓資料在程式重啟、機器重開之後還在。
但遊戲 Server 的麻煩不是「會不會 INSERT」，而是 在哪個時間點寫、寫失敗怎麼辦、寫太勤會不會拖垮對局。

成本大致從低到高：

記憶體 → 本機檔案 → Redis → 資料庫 → 跨機房複製

權威對局狀態（誰站在哪、這幀血量多少）活在 Room 記憶體。
真正往下沉的寫入，應該發生在事件邊界，例如：

  • 登入／登出
  • 購買、領郵件、改綁定
  • 對局結束結算
  • 斷線後短時間保留 session（常用 Redis + TTL）

讀完這章，你要能畫一條線：線的這一側是 tick 熱路徑（只碰記憶體），另一側才是 writer／DB／佇列。

先跟 Python 對一下

Python 常見做法 Go／遊戲 Server 對應
請求結束 session.commit() 可以，但不要在 tick 裡 commit
Flask/Django 每個 view 碰 DB HTTP 後台 OK；對局迴圈不行
Celery 丟非同步任務 worker goroutine／有界 channel／外部 MQ
ORM 自動 dirty flush 明確決定「這次要不要持久化」

Python Web 裡「請求範圍＝交易範圍」很直覺。遊戲裡一幀不是一個 HTTP 請求——一秒可能 20 次 tick，每次都 commit 等於自找麻煩。

怎麼劃界（實務規則）

先背這三條，之後寫碼才不會飄：

  1. Tick 內：只改記憶體
    套用輸入、推進模擬、組廣播快照——到此為止。
  2. 命令成功且「這個結果必須活過重啟」：丟到有界 channel 給 writer
    例如購買成功、對局 Ended 要記結果。Room 不在熱路徑直接 db.Exec。
  3. 關房／關服：flush 還沒寫完的關鍵任務
    停止接新局 → 排空佇列（或標記重試）→ 再退出。細節在 I5、J3。

最小形狀可以想成：

tick 迴圈 ──(只改 mem)──► snapshot 廣播
                │
                │  只有「事件」才送
                ▼
         jobs (有界 channel)
                │
                ▼
            writer / worker ──► Redis 或 DB

還沒接真 DB 也沒關係：先把「誰准寫、何時寫」拆開，之後換 Postgres 只是換 worker 裡面的實作。

為什麼這樣設計

為什麼座標不該每 tick 寫 Postgres？

假設 20Hz、房間 100 人、每人每 tick 更新一次座標：

  • 一秒 ≈ 2000 次寫入只為了座標
  • 磁碟與連線池先哭，tick 還要等 I/O，延遲尾巴被拉長
  • 玩家感覺是「操作黏、廣播慢」，根因卻是你把冷儲存塞進熱迴圈

更關鍵的是權威位置：當下座標的真相在 Room。DB 裡存「進行到一半的座標」通常沒業務價值——進程掛了，這局多數 PvP 直接作廢或判無效，而不是從 DB 還原每一幀。

至少一次 vs 剛好一次

結算常聽到兩個詞：

  • 至少一次（at-least-once）：worker 可能重試，同一筆結果可能被處理兩次 → 你的結算邏輯要冪等（做兩次跟做一次結果一樣，或靠唯一鍵擋下來）。
  • 剛好一次（exactly-once）：端到端極難，成本高；實務多半是「至少一次 + 冪等」假裝成剛好一次。

崩潰時「進行中的那一局」能不能丟？多數休閒 PvP 可以接受丟。
帳號上的鑽石、倉庫道具 不能丟 → 必須有獨立、清楚的交易邊界（買成功才扣款＋入袋，失敗要可回滾或可對帳）。

進階可先略過

  • 有些設計會把「關鍵命令」先寫 Outbox 表 再非同步投遞，避免「DB 成功了但訊息沒送出」。I5 會再點到。
  • 跨區複製、讀寫分離是營運議題；先把單區邊界做對比較實在。

遊戲 Server 會用在哪

Arena Mini 教學可以不接 DB，照樣把邊界想清楚：

  • PhaseEnded（或你的 Ended）時：組一筆 match result（誰贏、時長、分數）
  • 同步寫檔／log 可以；正式環境比較像「丟進 jobs，讓 worker 寫庫」
  • 進行中的 x,y、輸入佇列：只在記憶體

之後你加「賽季積分」「解鎖皮膚」，那些才是 DB 交易；不要順手把 Room 結構體塞滿 SQL。

請丟掉的舊習慣

  1. ORM／Unit of Work 每個小更新自動 flush——在 tick 裡等於隱形每幀寫庫。
  2. 把 Redis 當唯一真相，關鍵資產從不備份到 DB——Redis 適合快與跨進程，不適合當金庫。
  3. 「先全部寫 DB 再說，慢了再優化」——遊戲熱路徑的錯誤分層，後面是結構性重寫，不是加個 index 能救。
  4. 房間物件直接持有 DB 把手在模擬迴圈使用——測試難、超時難、關服更難。

動手練習

必做

  1. 列出 5 個遊戲狀態（例如：座標、準備旗標、錢包餘額、排行榜分數、斷線重連 token），各標「記憶體／Redis／DB」。
  2. 用自己的話寫 3～5 句：為什麼玩家座標不該每 tick 寫 Postgres（延遲、負載、權威、崩潰語意都可寫）。

選做

  1. 假設「購買皮膚」跟「對局結束加分」兩件事，分別畫出：誰在哪個 goroutine 做、失敗如何重試、會不會發兩次獎。

常見坑

  • 把「能丟的進行中局」跟「不能丟的資產」用同一條寫入路徑——重試策略會互相打架。
  • 事件到了卻在 tick 裡同步寫庫「圖個簡單」——尖峰時所有房間一起結算，DB 會瞬間被戳穿。
  • 關服直接殺行程：佇列裡未寫完的結算蒸發；至少要有 drain 或落地再重放的計劃（I5、J3）。
  • 無界 buffer 無限累積待寫任務：記憶體先爆，背壓全無。
