I4 · 快取一致性：允許錯多久，比追求永遠正確實際

旁路快取、TTL、寫穿；遊戲裡哪些資料可以舊一秒，哪些不行。

cache

這章你會搞懂什麼

快取（cache）本質上會 跟正本不一樣——至少在某些瞬間。
工程問題不是「怎麼讓快取永遠正確」（那通常貴到等同不要快取），而是：

  • 可以錯多久？（TTL、失效策略）
  • 錯了影響有多大？（外觀顯示錯 vs 錢包少錢）
  • 誰是正本？（DB？Room 記憶體？）

讀完這章，你要能對每個欄位說：「這份快取舊 60 秒可不可以」，以及寫入後要不要刪 key。

先跟 Python 對一下

Python Go／後端
Django cache、functools.lru_cache 進程內 LRU、或 Redis 當分散快取
「先讀 cache，沒有再查 DB」 Cache-aside（旁路快取），一樣常見
更新 model 忘了清 cache 一樣是經典bug

權衡相同：快＝可能舊；要強一致＝路徑更長、更貴。

常見模式（先會這幾個）

模式 白話 你要接受什麼
Cache-aside（旁路） 讀：先問快取，miss 再打 DB 並塞回；寫：先寫 DB，再刪／改快取 寫後讀可能短時間看到舊的（若刪得晚或有競態）
TTL 設過期時間，到期自動沒 簡單；允許「最多舊 N 秒」
寫穿（write-through） 寫的時候同時更新快取 仍有併發競態；實作較煩

教學上最常用、也好講清楚的是：

讀: cache.get(key) → miss → db.load → cache.set(key, ttl)
寫: db.write(...)  → cache.delete(key)   # 刪比「改成新值」單純，少一種半新半舊

為什麼很多人口袋選「寫後刪」而不是「寫後更新快取」？
因為並發下「更新快取」比較容易跟別的寫交錯，留下錯值；刪掉讓下次讀自己載入，雖然多一次 miss，語意較乾淨。

為什麼這樣設計

遊戲裡「可舊」跟「不可舊」

資料 通常態度 原因
角色外觀、稱號、設定表 可長 TTL 錯一下只是顯示；正本在 DB
排行榜展示 可短延遲 玩家容忍「幾十秒後才追上」
錢包、購買、庫存 要強一致或版本號 錯＝客訴與客服工單
對局中血量、座標 不以跨服快取當權威 權威在 Room；快取亂指會穿模

「進行中的 Room 狀態」千萬別隨手丟進 Redis 當跨服真相——除非你做了非常完整的租約、版本、誰說了算。H 卷 sticky Room 就是在回避這團複雜度。

驚群（thundering herd）

熱 key 一過期，瞬間一萬個請求一起 miss、一起打 DB，DB 會被自己人打掛。
進階作法是 singleflight（單飛）：同一個 key 只有一個載入在飛，其他人等結果。先知道有這問題；真遇到熱點再加。

版本號／CAS

資產更新可用「讀版本 → 寫入時檢查版本」或 DB 條件更新，避免用過期快取蓋回正本。
這比「無限 TTL 快取使用者餘額」安全太多。

進階可先略過

  • 延遲雙刪、訂閱 binlog 失效——營運級方案，新手先 TTL＋寫後刪就好。
  • 本地快取＋Redis 兩級：除錯時要分得清你看的是哪一層。

遊戲 Server 會用在哪

  • 大廳展示：皮膚、戰績摘要 → cache-aside + TTL。
  • 商城扣款：以 DB 交易為準；快取只當讀側加速，寫完一定失效。
  • 對局：血量／座標以 Room 廣播為準；客戶端預測可以舊一點，但 Server 權威不靠「共享快取糊過去」。

Arena Mini 現階段甚至可以沒有快取層——但你要能解釋「若加外觀快取，更新外觀時鍵怎麼刪」。

請丟掉的舊習慣

  1. 使用者資產設無限 TTL——掛機三天看到的還是鬼餘額。
  2. 更新 DB 卻忘了失效快取——客服最常接到的「我明明買了怎麼還沒有」。
  3. 把 Room 權威狀態快取成跨服唯一真相——除非你真的在做那套分散狀態機器。
  4. 所有讀都先打 Redis「圖個統一」——多一跳延遲，還多一個錯誤來源。

動手練習

必做

  1. 選兩個欄位：一個可以 TTL 60 秒，一個必須強一致。各寫原因（錯了誰受傷、怎麼修復）。

選做

  1. 用文字走一遍競態：A 讀到舊快取、B 寫 DB 並刪 key、A 又把舊值寫回快取——你的策略如何降低這件事？（提示：寫後刪、短 TTL、版本號。）

常見坑

  • 只寫快取不寫 DB：重啟或淘汰後資料蒸發，還以為存成功了。
  • null 也瘋狂快取：短時間內「沒這人」被記住，剛註冊的使用者一直 miss 邏輯錯亂——若快取空結果，TTL 要更短。
  • 失效鍵名算錯：寫的是 user:1:profile，刪的是 profile:1，等於沒刪。
  • 以為 TTL＝一致：TTL 只是「錯的上限」；不是交易。
