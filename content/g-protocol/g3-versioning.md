## 這章你會搞懂什麼

客戶端**不會**在同一天全部升級——尤其是 App Store／Play 商店審核還會拖。協定一開始就要想：**舊客戶端連上來怎麼辦？**

務實三件套：

1. **顯式版本**：信封上的 `"v": 1`  
2. **向後相容**：舊客戶端還能玩，或被**優雅拒絕**並提示更新  
3. **棄用窗口**：雙支援 → 打點告警 → 到期移除  

## 先跟 Python 對一下

HTTP API 常做 `/v1`／`/v2`——同一思想。即時遊戲訊息更常在**每則 JSON 內**帶 `v`，因為一條 WS 上會混很多 type，不靠 URL 分版。

「還沒人用就直接改欄位」在小專案賭得過，一上線有真實使用者就會炸。

## 怎麼寫（能跑的最小例子）

```go
if env.V != 1 {
	return fmt.Errorf("unsupported version %d", env.V)
}
```

範例 `examples/g01-envelope` 的 `Parse` 已拒絕非 1 的版本。

也可以：

```text
v1 → parseV1 → 內部模型
v2 → parseV2 → 同一內部模型
```

伺服器內部只認一種模型，對外暫時翻譯兩種電線格式。

拒絕時記得回應用層錯誤，例如：

```json
{ "v": 1, "type": "error", "payload": { "code": "UNSUPPORTED_VERSION", "msg": "please update" } }
```

（`v` 用對方看得懂的回應版本，或固定用最小共通版本——團隊要約定。）

## 為什麼這樣設計／底層在幹嘛

1. **什麼變更算「可相容」**  
   - 多半安全：加**可選**欄位、舊端忽略未知鍵（JSON 預設行為幫得上忙）  
   - 常要 bump `v`：刪欄位、改語意、改型別、同一欄位從「秒」變「毫秒」  

2. **為什麼要棄用窗口**  
   直接「只收 v2」會讓舊客戶端集體無法玩。先雙支援並打 log／metrics 看還剩多少 v1，再下線。

3. **文件化最低客戶端版本**  
   跟產品／營運同一張表：最低支援版、警告版、拒絕版。

4. **行動商店延遲**  
   強制更新視窗往往比 Web 更長——協定兼容策略要更保守。

5. **測試**  
   留幾則「舊版樣品 JSON」當相容測試；改協定時跑它們。

## 遊戲 Server 會用在哪

- Arena／正式遊戲的 WS 信封 `v`  
- HTTP API 可同時用路徑版本（`/v1/rooms`）  
- 熱更新設定與客戶端能力交涉（進階）  

## 請丟掉的舊習慣

1. **默默改 JSON 形狀就上線。**  
2. **用「還沒人用」當唯一相容策略。**  
3. **同一 `v` 卻改掉語意**——比加欄位更可怕，除錯者會瘋。

## 動手練習

### 必做

1. 為 envelope 拒絕 `v != 1`，並構想回 `{type:"error", ...}`（範例已拒絕版本，可補錯誤事件形狀）。  
2. 寫一頁短 CHANGELOG：假設要加 `payload.skin`，你要不要 bump `v`？為什麼？  

### 選做

1. 模擬 server 同時接受 v1／v2：v2 多一個欄位，轉成內部 struct。  

## 常見坑

- **前端後端各改各的，沒對表。**  
- **只版本化其中一種 type，其他訊息忘了。**  
- **錯誤訊息沒說「請更新」**：玩家只看到斷線。
