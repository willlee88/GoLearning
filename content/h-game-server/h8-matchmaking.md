## 這章你會搞懂什麼

到目前為止，我們假設「人已經在同一房」。  
但產品上，玩家常常是從大廳按「開始配對」，系統才把他們塞進同一個 Room。

**匹配**（matchmaking）的最小責任：

> 把「在線且想玩的人」變成「同一個 Room 的成員」，並處理湊不齊、超時、拒絕進房。

這章你會：

- 寫得出 2 人匹配的偽碼／最小佇列  
- 分清「自動匹配」跟「玩家自建房／輸房號」  
- 知道匹配服務與房間服務狀態性質不同

Arena Mini 用**相同 room id**當手動匹配——完全合法的簡化，但你要知道它覆蓋的是哪一段。

## Python 對照

| 做法 | 說明 |
|------|------|
| 記憶體 `list` + lock | 單機 demo 夠用 |
| Redis list／ZSET | 多進程／多機共享佇列 |
| 每次請求雙層 for 掃全服 | 人一多就炸——請丟掉 |

概念上就是佇列：入隊 → 條件滿足 → 出隊並建房。Go 或 Python 都一樣，差異在併發原語（`sync.Mutex` vs `threading.Lock`／asyncio 鎖）。

## 怎麼寫（最小模型）

```go
type Queue struct {
	mu   sync.Mutex
	wait []string // player ids
}

// Enqueue：若湊滿 2 人，回傳新 roomID 並 started=true
func (q *Queue) Enqueue(id string) (roomID string, started bool) {
	q.mu.Lock()
	defer q.mu.Unlock()

	// 簡易去重：已在佇列就忽略或更新
	q.wait = append(q.wait, id)
	if len(q.wait) < 2 {
		return "", false
	}
	a, b := q.wait[0], q.wait[1]
	q.wait = q.wait[2:]

	roomID = newRoomID()
	createRoomAndInvite(roomID, a, b) // 真正專案會打房間服務
	return roomID, true
}
```

還要補的產品行為（偽碼也行）：

```text
玩家點「配對」
  → Enqueue
  → 若 started：通知雙方 roomID，等他們 Join／連上房間
  → 若未湊齊：客戶端顯示「尋找中…」

超時（例如 30 秒）
  → 打 Bot、放寬條件、或 Cancel 出隊
```

「通知進房」之後若有人拒絕／斷線，要有回滾：拆房、把還在的人重新入隊——**匹配成功 ≠ 對戰一定開始**。

## 自動匹配 vs 自建房

| | 自建房／輸房號 | 自動匹配 |
|--|----------------|----------|
| 誰決定室友 | 玩家社交／口頭約 | 系統依規則 |
| 實作複雜度 | 低（Arena Mini 這條） | 中～高 |
| 失敗模式 | 房號打錯、空房沒人來 | 久配不到、段位不公、重複匹配 |
| 適合 | 好友同樂、教學 demo | 大眾線上對戰 |

兩者可以並存：很多遊戲是「好友房」+「快速配對」兩入口，最後都進同一種 Room Runtime。

## 為什麼匹配常獨立想（甚至獨立部署）

回顧 H1：

- **匹配**：偏工作流／佇列，理想上較無狀態（狀態多在佇列與短暫請求）  
- **房間**：偏有狀態，Tick 與權威世界住在這裡  

這樣拆的好處：

- 房間卡死不一定讓「按配對」全站一起掛（視架構而定）  
- 房間可以按親和性調度；匹配可以水平加機器掃佇列  

單進程 demo 不必真拆服務，但**型別與 package 不要纏成一團**。

### 進階可先略過

- **分池**：段位、地區、網絡延遲、派對（party）一起排。  
- **彈性擴圈**：先嚴格匹配，超時放寬分差。  
- **避免重複匹配**：同一人不能同時在兩個佇列／兩房操作位。  
- 評分系統（Elo／MMR）是匹配的輸入，不是匹配本身——別一次全做。

## 遊戲 Server 會用在哪

本站現況：

- 玩家輸入相同 room id ≈ **手動匹配**  
- 自動匹配列為二期／你的練習題  

等你做 H10 Lab 時，先把「進房後的權威對戰」做對；匹配只是把人送進那扇門。

## 請丟掉的舊習慣

1. **每次請求雙層 for 掃全服玩家**找「有沒有人也在等」——O(n²) 與鎖競爭驚喜包。  
2. **匹配成功就當結束**，不管對方拒絕進房、連不上、進錯房。  
3. **匹配邏輯直接改房間 tick 狀態**，還持有 websocket——邊界再次崩壞。  
4. **用顯示名稱當匹配鍵**又不處理撞名——配到兩個 `Player1` 的地獄。

## 動手練習

### 必做

1. 寫 2 人匹配偽碼（入隊、湊滿建房、通知）。  
2. 用三點比較「自建房」與「自動匹配」的差異（誰決定室友、失敗怎麼辦、狀態在哪）。  

### 選做

1. 幫佇列加超時：30 秒沒湊齊 → 出隊並回 `match_timeout`。  
2. 設計 party（雙人預組隊）進 4 人房的規則：不能拆隊、不夠人就等。  

## 常見坑

- **同一玩家連點配對進佇列兩次**：配到自己或佔兩個名額。  
- **房間建立了但沒人 Join**：殭屍房要 GC（跟 H3 Ended／銷毀銜接）。  
- **匹配線程／goroutine 直接操作 Conn 寫長訊息**：匹配只該發「去哪個房」，連線細節留給 Gateway。  
- **把匹配當反作弊**：它解決的是「湊人」，不是「誰開掛」。
