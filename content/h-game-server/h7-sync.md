## 這章你會搞懂什麼

權威狀態算出來了——接下來要讓每個客戶端「看得到同一個世界」。  
這叫**狀態同步**（state synchronization）。常見路線：

| 策略 | 白話 | 優點 | 代價 |
|------|------|------|------|
| 全量快照 Snapshot | 每次把現在完整狀態丟出去 | 實作簡單、重連好做 | 頻寬隨狀態變大 |
| Delta／增量 | 只送「跟上次比改了什麼」 | 省流量 | 要基準幀、丟包要補、複雜 |
| 興趣管理 AoI | 大世界只送你附近的東西 | 人多時必要 | 實作與除錯都重 |

這章立場很明確：

> **Arena Mini／M4 用全量 JSON 快照就夠。先正確，再優化。**

過早上 delta，通常是在優化一個還沒正確的系統。

## Python 對照

概念一樣：你序列化一份 dict／dataclass 廣播出去。  
要注意的是**序列化成本**與**廣播放大**——Python 或 Go 都一樣會中招，只是 Go 通常比較扛得住 CPU，但頻寬賬單不會陪你演戲。

```text
每 tick：
  state = room.Snapshot()   # 同一瞬間的自洽畫面
  for each observer:
      send(encode(state))
```

## 怎麼寫（信封長相）

一種教學上常見的包法（跟 G 卷信封一致）：

```json
{
  "v": 1,
  "type": "state",
  "payload": {
    "phase": "playing",
    "tick": 12,
    "players": [
      { "name": "Ada", "x": 40, "y": 10, "score": 1 },
      { "name": "Bob", "x": 55, "y": 12, "score": 0 }
    ]
  }
}
```

重點：

- **`type=state`**：這是 Server → Client 的權威畫面，不是 Client 自稱  
- **帶 `tick` 或版本**：除錯與之後做 delta／和解較容易  
- **一份快照裡的資料要自洽**：同一個 tick 產出來，不要「半更新」時廣播

客戶端可以：

- 直接把角色 snap 到新座標（最簡單）  
- 或在兩次快照之間**插值**（畫面較順）——但**不要**用插值結果當權威寫回 Server

## 為什麼廣播會「突然變貴」

粗估（數量級直覺，不是精算）：

```text
出站流量 ≈ 人數 × 觀測者數 × 每秒廣播次數 × 每包大小
```

四人同房、每人都能看到全員、20Hz、每包約 200 bytes：

```text
4 × 4 × 20 × 200 ≈ 64_000 bytes/s ≈ 64 KB/s（整房量級）
```

看起來不大——但若變成 50 人同場面、每包 2KB、還加上觀戰，數字會非常醜。  
這就是為什麼大世界要 AoI，而小房間 demo 可以全量。

### 何時才需要 delta？

當你量到（或可預估）這些訊號再動：

- 頻寬或手機流量成為真實問題  
- 狀態很大（一堆實體），但每 tick 只動少數  
- 連線慢到全量包開始擠塞  

上 delta 前先具備：

1. 可靠的全量基準幀（重連、久沒收到時重送全量）  
2. 序號／tick 對齊  
3. 丟包時的補償策略  

### 進階可先略過

- **二進位協定**（protobuf／自訂 binary）比 JSON 省——但教學可讀性下降。  
- **優先級通道**：移動可以丟，命中結算不能丟。  
- **客戶端預測與和解**：跟同步策略正交，可疊加，但複雜度上升很快。

## 遊戲 Server 會用在哪

Arena Mini：每 tick 廣播全量 `players[{name,x,y,…}]`。  
人少、狀態小、正確性優先——這是對的取捨。  
你在 Lab 裡應把時間花在「權威對不對、相位對不對」，不是先上壓縮。

## 請丟掉的舊習慣

1. **每人一份長期分叉的本地真相**，偶爾對一下——最後各玩各的。  
2. **過早上 delta／壓縮／興趣管理**，系統還不能穩定跑完一局。  
3. **廣播半成品狀態**（鎖內改到一半就 encode）——別人看到瞬移、分數跳變。  
4. **讓客戶端「幫忙算完再告訴大家」冒充同步**——那是 H4 的權威倒退。

## 動手練習

### 必做

1. 估算：4 人、20Hz、每快照 200B、每人收到全房狀態——出站大約多少？寫下算式。  
2. 寫兩句話：什麼情況下你會從全量改 delta？（不要只寫「人多」——要有可觀察的痛點。）  

### 選做

1. 在 snapshot 裡加上 `tick` 計數，客戶端 log 出來，確認單調增加。  
2. 故意把廣播降到 5Hz，感受「省流量 vs 手感」——思考插值要不要上。  

## 常見坑

- **O(n²) 沒心理準備**：每人一份含全員的包，人數一多平方成長。  
- **重連後只收 delta**：沒有基準幀，畫面永遠對不齊——全量才是重連朋友。  
- **不同觀察者看到不同 tick 的拼貼**：廣播前先固定 snapshot 變數，再對每人送同一份。  
- **為了省事把不同房間的人丟進同一個廣播列表**：串房是同步 Bug 也是隱私事故。
