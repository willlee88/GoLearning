## 這章你會搞懂什麼

**Redis** 是記憶體為主的資料結構伺服器，遊戲後端很愛用它，但愛用 ≠ 什麼都該扔進去。

這章不教你背完整命令手冊，而是先建立 **用途地圖**：什麼問題適合 Redis、什麼問題它只是看起來方便其實會害你。讀完你要能做決策，而不是「專案裡有 Redis 所以座標也寫一份」。

單機、單進程的 Arena Mini **可以不裝 Redis**。痛點通常出現在：多個 Gateway、多個 Game 進程、要跨機器查「這人在線嗎／在哪個房」、要做即時排行榜的時候。

## 先跟 Python 對一下

| Python | Go |
|--------|-----|
| `redis-py` | 常見如 `go-redis` 等客戶端 |
| `r.set` / `r.zadd` / `pubsub` | 同概念，命令語意一致 |
| 把 Redis 當 cache 或 broker | 一樣要分清：快取、訊息、還是「差點當 DB」 |

指令集相似；差別在你怎麼嵌入 Go 的生命週期（`context` 逾時、連線池、關服時不要半吊子下指令）。

## Redis 在遊戲裡常幹嘛

| 用途 | 常見結構 | 白話備註 |
|------|----------|----------|
| 在線 presence | `SET`／`HASH` + **TTL** | 心跳續期；過期＝當離線 |
| 排行榜 | `ZSET`（有序集合） | 按分數排序、取 top N 很快 |
| 跨進程房間訊息 | Pub/Sub | **廣播用**，不是可靠隊列 |
| 匹配佇列 | `LIST`／`ZSET` | 入隊出隊要注意原子性 |
| 分散鎖 | `SET key NX EX` | 能用但易踩死鎖／誤刪；要小心 |
| 短 TTL session／重連票 | 字串或 HASH + TTL | 斷線寬限期內有效 |

口訣補強 I0：

- **錢與庫存** → DB 交易  
- **跨進程且丟了可接受** → 可考慮 pubsub  
- **要排行／TTL／共享計數** → Redis 常是好選擇  
- **只在一個進程裡的權威對局** → 記憶體就好  

## 怎麼做決策（決策樹）

問自己四題，幾乎就能選層：

1. **資料只活在一個 Game 進程，而且掛了這局可丟？**  
   → 記憶體（Room）。別多寫一跳網路。  
2. **要跨進程通知，且漏訊可接受（例如「某房人數變了」刷新）？**  
   → Pub/Sub 或短 TTL 快取。  
3. **要排序、要自動過期、要多實例一起讀寫同一份「軟狀態」？**  
   → Redis。  
4. **扣款、道具、儲值、必須對帳？**  
   → DB 交易；Redis 頂多當旁路加速，不能當唯一帳簿（見 I4）。

鍵名先約定清楚，之後才好營運：

```text
presence:{userId}          # 心跳，帶 TTL
room:{roomId}:members      # 成員集合或人數
leaderboard:season:{id}    # ZSET 分數
matchq:mode:{mode}         # 匹配佇列
lock:order:{orderId}       # 鎖（慎用）
```

## 為什麼這樣設計

### Pub/Sub 為什麼不能當結算隊列？

訂閱者離線、進程重啟、網路抖一下：**那段時間的訊息就沒了**（至少在經典 Pub/Sub 語意下）。  
對局結算、發獎需要「至少一次＋可重試＋可對帳」。那是 I5 的有界佇列／外部 MQ／Outbox，不是 `PUBLISH` 了事。

### 為什麼 presence 一定要 TTL？

沒有過期的「在線」鍵會堆到宇宙毀滅。心跳續期的意思是：客戶端或 Gateway 定期 `EXPIRE`／再 `SET`；人斷線一段時間沒續，鍵自己消失，別人查就當離線。這比你自己掃一整表「最後時間」單純得多。

### 熱 key／大 key

排行榜、全服計數如果集中在少數鍵，或一個 HASH 塞幾十萬欄位，單分片／單執行緒那邊會先燙傷。鍵設計與拆分是擴展時才痛，但地圖階段就要知道「有這個坑」。

### 進階可先略過

- Redis Cluster 槽位、旁路快取與 I4 一致性。  
- Redlock 等分散鎖爭議：能不用業務鎖就靠 DB 唯一約束，常常更穩。  
- Stream 型資料結構可以做較可靠的消費者組——那是「队列」方向，別跟經典 Pub/Sub 混為一談。

## 遊戲 Server 會用在哪

典型分工：

- **房間權威狀態**仍 sticky 在某一個 Game 進程的記憶體（H 卷那套）。  
- Redis 幫忙：**發現**（這人在哪個進程／哪個房）、**旁路資料**（外觀快取、排行）、**廣播輔助**（跨 Gateway 提示）。  
- 單進程教學 demo：邏輯先寫對；Redis 當「水平擴展才插上的模組」，不要一開始就到處 `GET/SET` 干擾 tick。

## 請丟掉的舊習慣

1. **把 Redis 當永久 DB**——預設心智應是「會丟、要能重建、關鍵要有正本」。  
2. **session／presence 不設 TTL**——記憶體與鍵空間默默暴漲。  
3. **用 pubsub 發獎、扣款、結算**——漏訊時錢對不上。  
4. **「先全部進 Redis，以後再搬」**——搬正本比一開始分層更痛。

## 動手練習

### 必做

1. 設計 3 個 key 命名（含用途、建議結構、要不要 TTL）。  
2. 用自己的話說明：**為什麼 pubsub 不能取代「可靠結算隊列」**。  

### 選做

1. 畫多 Gateway＋一 Game 的示意：誰寫 presence、誰讀「玩家在哪」、Room 權威仍在哪。  

## 常見坑

- **鍵沒命名空間**：環境一多（dev/stage）互相踩、清不掉。  
- **大 key 一次 `KEYS *` 或全量撈**：阻塞、超時、雪崩。  
- **鎖的過期比臨界區還短／還長**：誤刪別人的鎖，或死鎖到天荒地老。  
- **以為 Redis 開了 AOF 就等於銀行級安全**：仍要看業務有沒有第二正本與對帳。
