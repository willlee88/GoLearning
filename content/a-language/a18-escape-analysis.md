## 這章你會搞懂什麼

Go 會自動管理記憶體，但不是「什麼都隨便 new」。編譯器做**逃逸分析（escape analysis）**：  
變數若證實只在函式內用，可能留在 **stack（堆疊）**；否則會上 **heap（堆積）**，交給 GC 回收。

你要的不是背完整規則，而是建立直觀：**熱路徑少做不必要分配**，並用工具看編譯器怎麼判斷。

## Python 對照

CPython 裡物件幾乎都在堆上，你比較少想「這個區域變數會不會逃逸」。  
Go 有機會更省、更可預測，但寫法讓大量東西逃到 heap，一樣會變「狂配＋GC 壓力」——遊戲 tick 特別明顯。

## 怎麼寫

看逃逸提示：

```bash
go build -gcflags="-m" .
```

輸出裡常見 `escapes to heap` 這類字樣。  
範例：`examples/a18-escape`——先猜哪種寫法更容易逃逸，再對答案。

## 細節

### 常見讓變數上堆的原因

- 回傳局部變數的指標（生命週期必須超出函式）  
- 把值裝進介面（介面要能裝「任意動態值」）  
- 閉包捕獲變數，使生命週期變長  
- 東西太大，不適合放 stack  

記住：上堆不是罪惡，是機制。問題是**熱路徑無謂上堆**。

### 優化順序

1. 先把算法與資料流做對  
2. 再減少重複分配（預先 make、重用 buffer）  
3. 最後才微觀到某一行有沒有逃逸  

沒有 profile 的微優化，多半是在浪費人生。

### 進階可先略過

- `sync.Pool` 重用 buffer（一定要注意生命週期，別把還在用的切片放回去）  
- `pprof` 的 heap 剖面跟 `-gcflags=-m` 對照著看  

## 遊戲 Server 會用在哪

每個 tick 對 N 個玩家都 `json.Marshal` 一份完整狀態，分配會很可觀。方向包含：

- 重用 buffer  
- 降頻／只對感興趣的人廣播  
- 改送 delta（見 H7／J6 一帶）  

先量哪裡貴，再改；別一開始就為了逃逸把程式寫到沒人敢維護。

## 請丟掉的舊習慣

1. 過早微優化，功能都還沒對。  
2. 不跑 pprof／benchmark，只靠「我感覺」。  
3. 把「全部改成指標」或「全部改成值」當萬能加速法。

## 動手練習

### 必做

1. 對範例跑 `-gcflags=-m`，讀懂至少兩行輸出。  
2. 猜一種寫法比較容易逃逸，再驗證。  

### 選做

1. 對一個小函式比較「回傳值」vs「回傳指標」的逃逸提示差異。  

## 常見坑

- **看到 escapes 就恐慌大改**：先確認它在不在熱路徑。  
- **為了不下堆引入複雜別名與生命週期 bug**。  
- **忽略配置本身**：算法 O(n²) 比逃逸細節痛一百倍。
